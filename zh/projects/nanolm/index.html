NanoLM

用 PyTorch 从零构建 GPT 风格 transformer——BPE 分词、训练循环、自实现 LoRA 微调——以流式本地聊天提供服务。

功能展示

  • 从零实现 GPT：分词 → 数据 → 模型 → 训练 → 采样
  • 自实现 LoRA 微调（仅 1.6% 参数可训练）
  • 实时生成参数控制（temperature · top-k · 惩罚项）
  • 微调前后对比（由真实 checkpoint 生成）
  • FastAPI 流式推理 + 聊天 UI

实测结果

  • 预训练：28.3M 参数 GPT，8GB 笔记本 GPU 上 6000 步 28 分钟（29–87K tok/s），loss 9.50 → 0.10，最佳验证 5.02；BPE 分词器（12000 词表）往返精确。
  • LoRA 微调：28 个适配器、仅 1.60% 参数可训练（0.459M）、442/49 指令对、3 分钟 val loss 4.03 → 0.84；微调前输出乱码，微调后能正确回答中毒性问题。
  • 留出评测协议 v2（44 条手写题、3 个随机种子、词边界匹配、启用极性判定）：命中率 30.3%，合并 95% 置信区间 [23.1%, 38.6%]。
  • v1 的 38.6% 是子串匹配虚高的（“cook” 被 “cooking” 命中）；同一批答案在修正规则下只有 31.8%。
  • 最不舒服的数字是基线，而我把它报了出来：在微调答案上做纯关键词查表就有 59.1%，比这个 28M 参数模型高约 29 个百分点。
  • 37 万 token 上跑 133 个 epoch（仅 Chinchilla 最优预算的 8.7%），val 在 step 1200 触底后回升——预训练记住的是措辞，LoRA 教会的是回答格式而不是知识。
  • KV 缓存：断言带/不带缓存逐 token 一致，CPU fp32 77.5→205.0（2.65×）、CUDA fp32 82.3→301.1（3.66×）、CUDA bf16 96.2→288.1（3.00×）。
  • 同一基准还暴露出：v1 的重复惩罚每步花 11.8ms 在设备同步上，并导致 bf16 下解码索引越界——两者均已修复。
  • 真 token 级 SSE 流式（首 token 约 0.6 秒），推理完全本地、零 API 成本。
  • CPU 与 CUDA 采样现在跨种子逐字节一致（132/132 条答案），而 v1 违反过这点——同一 checkpoint 在 CPU 上 52.3%、CUDA 上 38.6%。
