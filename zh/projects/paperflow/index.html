实测结果

  • 让其余一切成立的设计：引文核验由代码完成，而不是再问一次模型。它立刻暴露了核验器自身的缺陷——对归档 run 的 131 条论断全量重算，26 次"未找到"里有 24 次是它自己的问题（PDF 换行连字符、抽取噪声插入的数字）。命中率从 102/131（77.9%）到 130/131（99.2%）；唯一残留的一次是真的不在论文里的引文，所以这次修复消除了假阴性且没有换来任何假阳性。
  • 把归档报告与机器判定对账，暴露出项目此前无法察觉的失效模式：17 份报告里有 11 份与判定不一致，38 条论断已被降级却仍写作"有据"。现在报告会生成由代码写入的核验台账，并在生成后做一致性校验；工具层抓取会逐跳拒绝私网地址（用真实绑定在 127.0.0.1 的服务验证过）。
  • 四个 Agent 的流水线比单次长 prompt 强吗？用真实调用实测：三臂 × 各 5 次重复。结论是流水线没有买到质量，买到的是可审计性——14 条贡献清单的覆盖度：单次 prompt 14.0（区间 14–14）、流水线 13.4（13–14）；区间重叠，且流水线在 5 次里有 2 次也拿到满分 14/14。两者事实错误都是 0。
  • 这里要撤回一个上一版的结论：三次重复时覆盖度看起来是分离的（14/14 对 13/14），我当时就是这么写的；扩到五次重复后区间重叠，所以能站住的表述只有"本样本内未测得质量差异"。用同一批已存报告重评还显示：重叠在 n=3 时其实就已经存在——那个"分离"是三样本的噪声。
  • 流水线独有的产出：每条论断都带一条代码能在原文定位到的引文（机器层：9.8/9.8 条，100%），且报告里有一份由代码而不是模型写入的核验台账（5/5 轮）。单次 prompt 那一臂根本没有 claim 产物，所以它的引文无从核验。有一个离线 fixture 证明台账是承重的：当 Reader 编造引文时，流水线会把那条 bullet 改写成 [unverified] 并记入台账，而关闭核验的那一臂照样以 [supported] 交付。
  • 成本是唯一跨样本量稳定的列：每次审阅贵 4.31 倍（¥0.1138 对 ¥0.0264），按调用逐次记账——9 次 LLM 调用对 1 次。所以诚实的表述是一笔交换而不是胜利：多付约 4.3 倍，换来"论断可以被 LLM 之外的东西检验"。波动也如实说：流水线逐条的"可定位引文率"并不稳定（各次运行 0.0–0.182），这说明跑一次流水线的结果不该被当作稳定值。
  • 一条值得明说的测量限定，因为这正是这类实验最容易撒谎的地方：第一版评分器给出每臂 1.7–2.3 个事实错误，逐条核对后发现全是评分器自己的 bug（把 "Group E: A=44.2%, B=54.6%, C=53.8%, E=68.8%" 这种一句话两两比对，凭空造出 5 个"张冠李戴"；又把一次合法的减法当成编造）。修完用同一批已存报告重新评分（零新增 API 调用），各臂事实错误全部为 0。另外一次产物完整性审计发现：原来 9 个 run 目录里有 4 个在测量之后被覆写过，所以已发布的 n=3 数字是从 git 里原样冻结保留的，并把两种读法连同时间戳并列展示。
