功能展示

  • 结构化字段抽取，带逐字段置信度信号
  • 声明式规则引擎：重复 / 算术 / 税率异常
  • 交互式知识图谱探索——对象筛选、节点聚焦、关系图例
  • 发票详情抽屉：置信度条、审计证据、图谱关联
  • 审计统计图（按规则 / 按严重级）

实测结果

  • 字段级准确率 94.1%（原 82.5%）：30 张合成发票、真实 qwen-vl-plus API，抽取器修复后重测。
  • 逐字段：日期、购销方名称 100%，发票号与税额 96.7%，价税合计 93.3%，购方税号 83.3%，销方税号 75.9%。
  • 字段准确率只说明票据被读对；审计是否标对是另一件事，单独度量。
  • 喂入标注字段值时，7 类注入异常上引擎取得 micro P = R = F1 = 1.000（12/12 异常、0 误报）。
  • 这是“检测器与生成器一致”的结果而非泛化：标注由合成生成器写入，且它施加的正是每条规则要找的那个扰动。
  • 这个 1.000 在真实 OCR 下并不成立——喂入视觉模型实际返回的结果，micro F1 先降到 0.676。
  • 修好抽取器后同一套测量给出 P 0.733 / R 0.917 / F1 0.815，逐轮波动从 0.16 收敛到 0。
  • 端到端跑出的最高价值缺陷是存活率而非准确率：12.2% 的抽取尝试直接失败，全部是同一种“模型返回 JSON 格式错误”。
  • 解码侧修复层把失败率降到 0%（90/90 全部读出、41 份响应需修复），全批准确率 0.8272 → 0.9411（+11.4 个百分点，三轮均值，区间 0.9398–0.9436）。
  • 修复的第一版是错的、被重测抓出：失败率归零，却产出 18 个“自报置信度 1.0、值却是 0.0”的字段。
  • 原因：模型在正确文档之后又把行项目模板作为顶层键重复输出，JSON“后者覆盖”让占位符盖掉了已读对的值——改为首次出现优先。
  • 修复只恢复 JSON 框架、绝不造值：内部自相矛盾的 payload 直接拒绝，完全不含发票字段的文档仍判失败。
  • OCR 误差是双向的，一张票就能看全：模型把实在 656.09 的金额写成 706.09，文档因此内部自洽，注入的算术异常就此静默。
  • 同一个错误数字又与从像素解码出的二维码对不上，于是在本无该类异常的票上凭空造出一条告警。
  • 兜底如实标注为未验证：配置的备用模型在本环境返回 403、从未被调用；纠错重读在 90 份文档里只触发 1 次。
  • 成本与规模随修复一起变：每轮 ¥0.3605 → ¥0.3138，单张 16.7 s → 12.9 s；10 万张外推从约 ¥401 / 148 小时 / 1.2 万张待人工复核变成约 ¥349 / 92 小时 / 0。
  • 8 条带严重级与证据的审计规则，含二维码交叉校验与 GB 32100-2015 税号修复。
  • 两个会让审计静默失效的失败模式已修复并有回归测试：全部文档失败时不再报成功；单条规则崩溃不再丢掉整批告警。
