实测结果

  • 30 张合成发票真实 API 基准（qwen-vl-plus）：字段级准确率 82.5%——发票号 86.7%、日期 90.0%、购销方 86.7%、金额 80–86.7%、税号 70–72%。
  • 字段准确率只说明发票被"读对"了，完全不说明审计是否标对了——所以这件事单独度量。喂入标注字段时，7 类注入异常上引擎取得 micro P = R = F1 = 1.000（12/12 异常、0 误报）。但要说明白：这是"检测器与生成器一致"的结果，因为标注由合成数据生成器写入、且它施加的正是每条规则要找的那个扰动。
  • 而这个 1.000 在真实 OCR 噪声下并不成立——所以这件事也被度量了。把视觉模型实际返回的结果喂进引擎，指标降到 micro P 0.66 / R 0.69–0.81 / F1 0.68–0.72（3 轮 × 30 张）。一次误读会同时制造两个方向的错误：某张票的合计被读成 706.09（实为 656.09）后文档变得内部自洽，注入的算术异常就此静默；而同一个错误数字又与从像素解码出的二维码对不上，凭空制造出一条告警。
  • 还有两个真实部署必须规划的事实：约 12% 的抽取尝试直接失败（全部是同一种"模型返回的 JSON 格式错误"，而配置的兜底模型整场调用都返回 403），这一轮实测花费 ¥0.36、单张平均 16.7 秒——外推到 10 万张约需 ¥401、4 并发下约 148 小时，并且仍有约 12,000 张需要人工复核。
  • 8 条带严重级与证据的审计规则，含二维码交叉校验与 GB 32100-2015 税号修复。两个会让审计"静默失效"的失败模式已修复并有回归测试：全部文档抽取失败时不再报成功；单条规则崩溃不再丢掉整批告警。
